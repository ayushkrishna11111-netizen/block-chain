1. What is happening (how the system works)

The system is a full-stack Student Information System (SIS) where managing academic records is the product and trustless verification is one integrated feature. Academic data lives in MySQL 8 (the mutable source of truth); the blockchain stores only immutable evidence.

  • Issuance. An ISSUER/ADMIN wallet session compiles a canonical, key-sorted transcript JSON from live grades, computes a SHA-256 digest (of an uploaded PDF's exact bytes when supplied, otherwise of the canonical JSON), stores the record as DRAFT, anchors the digest + IPFS CID + issuer + timestamp on the AcademicRecordManager contract, and only then marks it ACTIVE. A failed transaction can never appear as issued (DRAFT + retry endpoint).
  • Lifecycle. Records transition Active → Revoked or Active → Superseded. A correction (supersession) publishes the new record and retires the old one in a single atomic transaction, with the replacement link stored on-chain.
  • Verification (integrated feature). Anyone verifies by record ID or by dropping the document: the digest is computed in the browser, looked up through a read-only eth_call (zero gas, no wallet) and cross-checked against MySQL. The response reports database status, chain status, an explicit consistency flag (status and digest must match — direct database tampering is flagged), and the issuer credential signature. Unknown IDs return 404; a chain outage is reported as unavailable, never as tampered.
  • Identity & RBAC. Password-less MetaMask personal_sign login produces stateless 12-hour session tokens (no server secret). Roles ADMIN/ISSUER/STUDENT/VERIFIER are enforced by the API and independently by the contract's issuer whitelist — the ledger cannot be written by an unauthorized wallet even if the API were bypassed.
  • New in this build. QR codes and shareable /verify/<id> links; browser-side (MetaMask) signing of issuance/revocation transactions with server-signer fallback; AES-256-GCM encryption at rest for stored PDFs; issuer signature over the record digest, re-verified publicly; a 23-mutation tamper suite and an automated chain-outage failure-path test.

Honest limitations. Sepolia deployment and Pinata pinning are fully wired (env-configured) but were not exercised here — no funded testnet key or Pinata JWT was available. The credential signature is an issuer wallet signature over the record digest, not a W3C Data Integrity proof; no standards compliance is claimed. QR codes link to the verification page; camera-based QR scanning is not implemented. Wall-clock timings are from a local automining node; public-network timings will differ.

3. What more can be built

  • W3C Verifiable Credentials 2.0 + DID methods — issue credentials as full VCs with Data Integrity proofs and a status list for revocation, enabling ecosystem-wide interoperability (EBSI, 1EdTech Open Badges).
  • Public-network rollout — Sepolia → mainnet/L2 anchoring (Polygon/Arbitrum for cost), multi-institution issuer governance ( multisig admin, per-faculty whitelists), and measured public-network latencies.
  • QR scanning and offline verification — camera-based QR capture, a PWA mobile wallet, and an offline-capable verifier that caches Merkle proofs.
  • Zero-knowledge selective disclosure — prove "GPA ≥ 3.5" or "degree conferred" without revealing the full transcript (ZKBAR-V-style), keeping privacy while retaining verifiability.
  • IPFS hardening — pin via Pinata/web3.storage with redundancy, encrypted CID publication, and gateway health monitoring.
  • Registrar tooling — batch issuance CSV import, cohort statistics, LMS/ERP integration (SIS connectors), and automated degree-audit checks before issuance.
  • Security operations — key-ceremony/HSM for the server signer, key rotation, alerting on anchor failures, and a public audit explorer over contract events.
